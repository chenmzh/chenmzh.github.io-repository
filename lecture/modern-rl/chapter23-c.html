08训练放在可重置沙箱里：先模仿定位，再在线学习完整任务

GUI 在线强化学习会主动制造失败轨迹。训练环境必须隔离真实账号与文件，并能把每条轨迹恢复到相同初态。

Virtual Machine（VM，虚拟机）快照可以在每次 rollout 前恢复应用、文件与账号状态，使不同策略从同一个起点比较；沙箱则限制网络、凭据与宿主文件访问。

04 · STATE VERIFIER读取应用状态而非成功文案返回任务与安全分项

训练链的依赖关系是：没有视觉与演示冷启动，在线轨迹几乎都在前几步失败；没有可重置快照和结构化验证器，reward 又无法可靠表示任务是否真正完成。

最简单的终点奖励是 $r_T=\mathbb 1[\text{task completed}]$。长任务还可以加入格式、进度与非法动作信号：

$$r_t=r_{\mathrm{task},t}+\lambda r_{\mathrm{progress},t}-\mu r_{\mathrm{invalid},t}.$$

但进度验证器也会犯错。例如页面出现“操作已受理”并不保证后台改对了订单；若 verifier 只匹配成功文案，策略会学会制造文案而不是完成任务。可靠验证应读取结构化应用状态，并检查对象、参数和副作用。

训练对象数据/环境它解决什么它不保证什么
Grounding SFT截图与目标区域元素识别、坐标定位动作时机与任务规划
轨迹 SFT演示或筛选成功轨迹动作顺序、恢复模板新界面上的探索能力
在线 RL可重置沙箱 rollout多步任务成功率真实世界自动获得授权

Insight 05

训练提高策略能力，门禁限制能力的后果

安全数据可以让模型更常主动停下，但运行时仍必须独立检查授权、动作对象与确认。反过来，门禁也不能替代定位和规划训练。

模型行为与系统执行是两层控制；把它们压成同一个 reward，会同时失去可学习性和安全性。

09评测不要只报成功率：沿轨迹找到第一处分叉

任务失败可能发生在看、想、点、等、验或安全门禁的任何一层。只有逐步保存截图、原始输出、解析动作和应用状态，才能知道该改哪里。

失败类型轨迹证据应优先修什么
视觉定位动作类型正确，坐标落在目标外跨分辨率 grounding 数据
任务规划点中了元素，但当前子目标不该做带任务上下文的轨迹
状态检查界面仍在加载却重复点击等待、预期变化与历史
动作解析坐标越界、组合键或参数非法动作格式与 parser
验证器显示成功但后台对象/参数错误结构化状态断言
安全边界越权动作被执行或合法任务被误拒授权、确认与安全切片
环境故障VM 崩溃、应用卡死、网络中断沙箱基础设施

分类的目的不是给失败贴标签，而是找到第一处因果分叉：早期误点会改变后面所有截图，不能把后续连锁错误都重复算成规划失败。

至少同时报告：任务成功率、目标区域命中率、平均动作数、无效动作率、环境错误率、单步延迟，以及安全切片中的确认遵循率、越权副作用率和合法任务误拒绝率。一个“什么也不做”的 Agent 攻击成功率为 0，却没有任何任务效用，因此安全与效用必须成对测量。

10把环境与门禁写成两层代码

环境负责截图、执行与 reset；门禁在执行之前拦截动作。训练策略不能绕过门禁直接访问鼠标键盘注入器。

class GUIEnv:
    def reset(self, task_id):
        self.vm.restore_snapshot(task_id)
        self.task = self.tasks[task_id]
        return self.vm.screenshot()

    def step(self, proposal, authorization, confirmation):
        decision = safety_gate(
            action=proposal,
            authorization=authorization,
            confirmation=confirmation,
        )
        if decision == "pause_for_confirmation":
            return self.vm.screenshot(), 0.0, False, {
                "gate": decision,
                "termination_reason": None,
            }
        if decision == "abort":
            return self.vm.screenshot(), 0.0, True, {
                "gate": "abort",
                "termination_reason": "safety_abort",
            }

        self.vm.execute(proposal)
        observation = self.vm.screenshot()
        completed = self.task.verifier(self.vm.app_state)
        return observation, float(completed), completed, {
            "gate": "executed",
            "termination_reason": "task_complete" if completed else None,
        }
def safety_gate(action, authorization, confirmation):
    if action.source_is_untrusted_instruction:
        return "abort"
    if not authorization.allows(action.capability, action.target):
        return "abort"
    if action.risk in {"high", "critical"}:
        if confirmation.state == "approved" and confirmation.matches(action):
            return "execute"
        if confirmation.state == "pending":
            return "pause_for_confirmation"
        return "abort"  # 明确拒绝、过期或对象不匹配的批准
    return "execute"
概念程序变量检查边界
像素观察 $o_t$observation截图尺寸、时间与应用标识
动作 $a_t=(k_t,\eta_t)$proposal类型、坐标、对象与来源
授权集合 $\mathcal A(C)$authorization能力、对象、参数与有效期
高风险确认confirmation必须精确绑定当前动作
真正任务状态vm.app_state不能只读截图中的成功文字
不可越过的边界

不要让训练策略在真实账号上“探索安全边界”。 高风险轨迹要在隔离账号、桩执行器或可重置 VM 中生成；部署时只有明确授权且经过门禁的具体动作才能影响真实系统。

11检查你的理解：从一次点击定位失败与风险边界

先遮住答案，尝试说清楚“模型错在哪里”和“系统应在哪一层阻断”。

1. 为什么当前截图不能直接当作完整 Markov state？
截图看不到网络请求、焦点、剪贴板、权限、后台上传等隐藏状态；相同像素可能分别对应“正在处理”和“根本没点中”。策略需要动作历史、时间与后续观察辅助判断。
2. click 为什么是混合动作？
动作类型 click 是离散选择，坐标、按键类型等参数又属于另一参数空间。GUI 策略必须同时预测要做什么以及作用在哪里。
3. 坐标准确点中“提交”，为什么仍可能是规划失败？
字段可能尚未填写、当前任务可能只要求查看，或界面还在处理上一请求。Grounding 只回答元素在哪里，不回答此刻是否应该执行该动作。
4. 模型有 98% 把握时，为什么转账仍可能需要确认？
风险同时由错误概率和失败损失决定。2% 乘以巨大且不可逆的损失仍然不可接受；确认还用于验证用户是否授权了具体收款人和金额。
5. PDF 要求 Agent 转发邮件，用户随后点击“批准”就一定可以执行吗？
不一定。低信任来源不能扩大用户原始授权；确认必须针对授权范围内、由系统清楚描述的具体动作。若原目标只是总结 PDF，跨应用转发邮件应直接中止。
6. 为什么在线 RL 与部署门禁不能互相替代？
在线 RL 在可重置环境中提高定位、规划与恢复能力；门禁在真实执行前限制授权和副作用。训练不能保证模型永不犯错，门禁也不能教会模型识别新界面。

第二十三章建立起来的双闭环

截图 + 历史
→
动作类型 + 参数
→
授权 / 风险 / 确认门禁
→

策略闭环负责从视觉反馈中完成任务，安全闭环负责限制动作何时能影响真实系统。前者追求能力，后者约束副作用；二者都必须保存可回放轨迹。
