08token pipeline：训练数据不是一段文本，而是一条带血缘的记录

规模化以后，“把 response 存下来”远远不够。训练必须知道哪些 token 参与 loss、谁生成了它们、为什么得到这个 reward，以及环境是否可重放。

data/token pipeline（数据与 token 流水线）是轨迹从任务进入生成端，到被编码、评分、组成训练 batch，再进入归档或回流的全过程。称为 token pipeline，是因为 LLM 的更新最终发生在 token 位置上：prompt token 通常只提供上下文，response token 才参与策略损失；padding、工具结果、截断位置与无效输出必须用 mask 区分。

01 · TASKprompt + task version来源、难度、模板、环境
→
02 · GENERATEtokens + maskslogprob、finish reason、policy version
→
03 · SCOREreward components规则、verifier、judge 与版本
→
04 · LEARNbatch + updatelag、loss、checkpoint

顺着箭头检查一条样本能否被复算：同一任务版本、生成策略、采样参数、token/mask 与奖励版本都必须可追踪；缺任一项，异常梯度就很难回到具体原因。

记录层最小字段字段缺失会怎样
任务prompt_id、来源、难度、模板/环境版本不知道提升来自哪类数据，也无法重跑同一任务
生成token_ids、response_mask、采样参数、finish_reason截断 token 可能被当正常结束，prompt/padding 可能误入 loss
策略policy_version、生成时 old logprob无法计算陈旧度，也无法判断训推概率差
奖励分项 reward、聚合权重、verifier/judge 版本、错误码高分可能来自服务故障或某个分项被绕过
系统worker、时间戳、seed、运行环境/checkpoint 标识同一故障无法定位到节点，也无法重放

数据吞吐不等于有效 token 吞吐

假设生成端每秒输出 30k token，但其中 20% 因超长截断无效、10% 因 verifier/环境错误被隔离，那么进入学习的有效吞吐至多是：

$$v_{\mathrm{useful}}=30\mathrm{k}\times(1-0.20-0.10)=21\mathrm{k}\ \text{token/s}$$

这只是互斥错误类别下的简化例子；若一条轨迹同时超长且验证失败，不能重复相减。真实系统应直接统计最终通过质量门的数据量。被过滤轨迹也不应静默删除：环境超时用于修沙箱，格式错误用于补 SFT，奖励异常用于查 verifier，只有明确的数据状态才能形成闭环。

容易想错

“reward 已经是一个标量，存总分就够了。” 不够。若总分突然变高，你必须知道是答案正确率上升、格式分增加、长度惩罚失效，还是 judge 版本改变。没有分项与版本，reward 曲线不能成为可审计证据。

09长训练要能恢复、能比较、能在出事前停下

集群跑得久以后，重启、评测和告警不是外围运维；它们决定一条结果能不能复现，以及异常是否会污染之后数小时的数据。

Checkpoint：保存“可继续训练的状态”，不只是模型权重

checkpoint（检查点）是在某一训练时刻保存的可恢复状态。只保存 Actor 权重可以做推理，却未必能无缝续训。恢复训练通常还需要优化器状态、学习率调度、混合精度 scaler、随机数状态、数据游标和当前 policy version；异步系统还要说明 buffer 如何处理。

MODELActor / adapter 权重恢复当前策略
OPTIMIZATIONoptimizer + scheduler恢复动量与学习率阶段
DATAcursor + policy version解释下一批从哪里开始
CONTRACTreward / environment version保证恢复后的世界没有变

四栏真正要检查的是一致切面：模型、优化器、数据位置和任务世界必须属于同一训练时刻。混搭 checkpoint 可能成功启动，却不会复现原来的学习轨迹。

这也解释了 checkpoint 与 weight sync 的区别：weight sync 是把最新推理所需参数快速送到 rollout 端；checkpoint 是把故障后恢复所需状态持久化。前者追求低延迟，后者追求完整与一致。

Evaluation worker：把“训练分变高”与“真实能力变好”分开

evaluation worker（评测进程）周期性加载一个明确 checkpoint，在固定且独立的任务集上运行固定协议。它不反向传播，也不直接消费训练 buffer；它回答的是这个版本是否值得保留或发布。

一个可信比较至少锁定模型权重、聊天模板、推理引擎、temperature、最大长度、工具权限、verifier 版本与任务集版本。否则两个 checkpoint 的分数差可能来自配置差，而不是能力差。训练 reward 与独立评测分离，是比 loss 更早暴露 reward hacking 的信号。

Monitoring：用三层面板定位，不用一个红灯猜原因

monitoring（监控）是持续采集指标、样本与告警条件，使训练在明显失稳或系统异常时及时停下。最小面板应把三层放在同一时间轴：

OUTCOME

模型结果

独立评测、任务成功率、通用能力回归、安全集。

LEARNING

策略与数据

reward 分项、KL、entropy、长度、优势方差、$\Delta v$、样本丢弃率。

SYSTEM

流水线健康

各 stage time、tokens/s、queue depth、sync time、GPU/MFU，以及 Out of Memory（OOM，内存／显存不足）等错误。

阅读顺序从左到右：先确认独立能力是否变化，再定位学习信号，最后解释系统原因。系统更快但 outcome 不涨，不算训练成功。

例如，queue depth 持续上升、$\Delta v$ 上升而 rollout tokens/s 很高，说明生产快于消费；不是 rollout 还不够快。又如 reward 上升、独立成功率不变且 response 长度贴住上限，应该先抽查输出与奖励规则，而不是继续堆 GPU。

Insight 05

工业训练的产物是一条可追踪闭环，不只是一个权重文件

checkpoint 让状态可恢复，评测契约让版本可比较，监控与轨迹血缘让失败可定位；三者共同决定“某次提升”能否被相信和复现。

没有数据、环境、奖励和模型版本的对应关系，规模越大只会越快地产生不可解释的结果。

11检查你的理解：你能从时间线定位瓶颈吗？

先遮住答案，尽量用“工作量—速率—时间—版本”的链条回答，而不是报出一个框架名。

1. 一轮 rollout 45 秒、reward 4 秒、training 12 秒。为什么把 training 加速两倍只能把 61 秒缩到 55 秒？
因为同步 step time 是各段耗时之和。training 从 12 秒变成 6 秒只省 6 秒，45 秒 rollout 完全没变；生成仍占主导。先优化最大时间项，才可能得到显著端到端收益。
2. rollout worker 与 inference worker 都“生成回答”，为什么仍要区分？
rollout worker 定义训练样本：挑任务、决定每题采几条、管理终止与 policy version；inference worker 高吞吐执行模型前向与采样，管理 prefill/decode、KV cache 和 batch。小系统可合并，大系统中职责与扩展瓶颈不同。
3. 为什么异步稳态批次间隔近似看最大 stage time，而不是把 tokens/s 相加？
各 stage 是同一数据必须依次经过的工序，不是共同生成同一种可直接合并的结果。流水线填满后，快阶段会等慢阶段，因此交付间隔受服务时间最长的一段限制。
4. buffer depth 持续增长说明什么？应先增加哪一端算力？
由 $dq/dt=\lambda_r-\mu_t$，持续增长说明 rollout 生产率大于 training 消费率。此时再加 rollout 算力只会积压更快；应检查 training/reward 消费、通信或减小生产速率，并同时观察 staleness 与丢弃率。
5. policy version 差 3 是否必然比差 1 更危险？
不必然。版本差是工程近似，实际行为差还取决于每次更新幅度。要同时看新旧策略对样本动作的 log-probability 或概率比；三次小更新可能比一次异常大更新更接近。
6. 为什么 GPU utilization 很高仍不能证明系统训练得好？
它只说明观察窗口里设备在执行 kernel，不能证明 token 有效、样本新鲜、reward 正确或独立评测提高。最终要把 outcome、学习/数据和系统三层指标放在同一时间轴解释。
7. weight sync 与 checkpoint 的目标有什么不同？
weight sync 把推理所需的最新 Actor 参数尽快送到 rollout 端；checkpoint 持久化故障恢复所需的一致状态，通常还含优化器、scheduler、随机状态、数据游标和版本契约。一个追求低延迟回流，一个追求完整恢复。
