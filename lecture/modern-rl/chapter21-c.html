07代码 RLVR：从执行结果到策略更新的最短线路

Reinforcement Learning with Verifiable Rewards（RLVR，可验证奖励强化学习）在 Chapter 16 已正式解释过：奖励由规则或程序检查产生。代码场景的关键变化，是 verifier 必须真的运行模型产物。

固定上游代码给出一个函数级实验：题目是 stdin/stdout 形式的竞赛程序，而不是仓库 patch。数据把输入输出用例保存在 reward_model["ground_truth"] 中；奖励函数依次提取 Python 代码、逐个运行测试、比较标准输出，再返回通过比例：

MODELsolution_str模型完整回答
→
PARSEextract_code提取 Python code block
→
EXECUTErun_io_testsstdin → program → stdout
→
REWARDscore = pass_rate交给 PPO 的标量

真正要观察的是最后一条接线：只有返回字典里的 score 进入策略奖励；format 只是独立日志指标，不能误写成“代码块格式也自动加分”。

def compute_score(data_source, solution_str, ground_truth, extra_info=None):
    match = _CODE_BLOCK_RE.search(solution_str)
    format_ok = 1.0 if match else 0.0
    code = extract_code(solution_str)
    if not code:
        return {"score": 0.0, "pass_rate": 0.0, "format": 0.0}
    pass_rate, detail = run_io_tests(code, ground_truth)
    return {
        "score": pass_rate,       # PPO 使用的主奖励
        "pass_rate": pass_rate,   # 诊断日志
        "format": format_ok,      # 是否输出了代码块，仅记录
    }
上游变量函数级 code RLVR迁移到仓库级环境
solution_str一段完整程序回答工具轨迹生成的最终 model_patch
ground_truthstdin/stdout 测试对任务测试、回归测试与运行合同

这张映射也揭示了一个边界：把函数级 reward 文件接入训练器，并不会自动得到仓库级 Agent。后者还需要文件工具、持久工作副本、状态重置、patch 应用、依赖镜像、隐藏测试和基础设施错误分类。

执行安全边界

上游实现明确拒绝把本地 subprocess 当成安全沙箱。子进程仍可能读取当前用户可见文件、网络和凭据。训练生成代码前，应先放进最小权限 container（容器）或 Virtual Machine（VM，虚拟机），清理凭据、限制网络与资源，并只读挂载训练数据；超时与内存上限只是附加限制，不能替代隔离。

Insight 05

硬反馈来自执行，不来自文件名叫 reward

训练器只有在数据里的验证条件、执行函数和主奖励字段正确接通时，才真的看见可验证结果。任何一处错接，都会出现“训练在跑、模型却没收到题目或奖励”的假进展。

先用已知正确、已知错误和空回答做 reward sanity check，再花 GPU 预算训练。

08一个可训练代码环境，至少要守住五条合同

把算法名从 PPO 换成 GRPO，不会修复一个不可靠的执行环境。下面五条是环境向策略承诺的可检查合同。

  1. 01
    同起点

    每条 rollout 从同一 commit、同一镜像与干净进程状态开始。

  2. 02
    动作留痕

    记录 observation、工具参数、输出、patch、token 与超时，而不只保存最终 diff。

  3. 03
    验证器隔离

    在只读基准副本上应用 patch；测试入口与受保护测试不能被 Agent 修改。

  4. 04
    失败分型

    断言失败、补丁冲突、依赖失败、容器故障和超时使用不同状态码。

  5. 05
    预算可比

    同时报告模型、工具权限、最大步数、采样数、token、时间与 Pass@k 口径。

这些合同决定了 reward 是否能归因给策略。例如容器没启动时返回 0，会把基础设施事故当成一次“坏动作”；若 Agent 能编辑测试入口，reward 又会鼓励它改变计分方式。两种错误方向相反，却都会污染策略更新。

MODEL FAILURE补丁应用成功，测试断言失败

这是可学习的任务反馈：实现没有满足当前合同。

INFRA FAILURE镜像、依赖或 runner 没有启动

这是环境数据质量问题：应重试或剔除，不能直接归罪策略。

真正要分开的是“代码被正确执行后失败”与“代码根本没有得到一次有效评测”。把两者都记成零分，会训练模型适应随机基础设施噪声。

09迁移类比：长轨迹让“预测后果”和“真实执行”同时重要

这里只做两次迁移定位，不重新教授 Chapter 10 的 world model，也不把公开工作未声明的组件写成既成训练配方。

WORLD-MODEL ANALOGY

一次 edit 之后，下一状态会怎样？

Chapter 10 的 world model（学习环境动力学）思想可以类比到代码：根据当前仓库与动作，预测下一份文件状态或测试日志。Code World Model（CWM，代码世界模型）一类工作提醒我们，模型可以从解释器与容器轨迹中学习软件执行规律。

边界：预测器会错，依赖和外部服务也难以完整模拟。候选最终仍要回到真实执行环境验证，不能让模型预测替代 ground truth test。

LONG-HORIZON ANALOGY

奖励在终点，前面几十步怎样改进？

一类长程代码智能体工作强调稳定环境、长 rollout 与可验证终态奖励。它与本章主线的联系是：补丁成功来自多步工具序列，而不只是一次代码生成。

边界：过程 shaping、value model 或搜索都是要单独消融的选择；不能因为任务很长，就默认某一种额外组件必然有效。

两栏共同指向同一条因果关系：模拟可以降低探索成本，真实执行负责纠正模拟误差；长轨迹需要更强的信用分配，但环境可靠性先于算法复杂度。

自生成缺陷与自我修复还可以扩大训练数据，但那会引入“题目是否有效、难度是否平衡、合成缺陷是否像真实 issue”等新问题。本章不展开自生成题目与自我改进的具体配方；它只强化一点：无论题目来自真实 PR 还是合成变异，都必须先证明仓库能运行、缺陷能被测试触发、修复后能回归。

10把主线收紧：环境先可信，奖励才可学习

代码智能体 RL 的最小闭环不是“模型写代码 → 跑一下 pytest”，而是把任务、状态、动作、执行、验证、重置与日志都写成可复现合同。

01 · TASKsnapshot + issue固定起点
→
02 · ROLLOUTread / search / edit / test产生轨迹
→
03 · PATCH$\Delta_T=\operatorname{diff}(C_0,C_T)$终点产物
→
04 · VERIFIER保护测试 + 环境日志形成奖励

链条任一环节不可信，最后的标量都无法干净归因给策略；算法只能放大环境给它的信号，不能自动修正缺失的测试合同。

本章四句话

  • 仓库状态包含源码、累积 patch 与执行环境；每条 rollout 必须从相同快照重置。
  • 最终 patch 只是轨迹终点，搜索、阅读、编辑、测试和返工才是代码 Agent 的动作空间。
  • 测试能提供规模化的 hard feedback，但测试不是普适真值；公开满分、完整通过率与 resolved 必须分开。
  • 函数级 code RLVR 与仓库级修复共享“执行 → reward”，后者还需要隔离容器、patch replay、隐藏回归和失败分型。

理解检查

1. 为什么只收集开发者最终 patch，不足以训练一个多轮代码智能体？
最终 patch 没有告诉模型应搜索哪个文件、怎样利用测试失败、何时回退或停止。多轮 Agent 的策略作用在整条 observation–action 轨迹上，而不仅是终点 diff。
2. 为什么同一任务的不同 rollout 必须恢复依赖、缓存和进程，而不只 reset 源码？
因为依赖与进程也是执行状态。若它们不同，测试结果差异可能由环境残留造成，奖励便不能只归因给策略动作。
3. 某补丁公开测试 2/2、隐藏测试 1/2。三个奖励分别是多少？
$R_{visible}=1.00$，四项合并通过率 $R_{all}=3/4=0.75$；只要任务要求全部必要测试通过，$R_{resolved}=0$。
4. 为什么 P1 的公开奖励与 P4 相同，不能证明策略学会了正确异常边界？
公开测试只检查普通列表和空列表，无法区分“只处理空容器”与“吞掉全部异常”。在相同代理奖励下，优化器没有信号偏爱语义更精确的 P4。
5. 上游 compute_score 中，format 会直接增加 PPO reward 吗？
不会。返回字典中的 score 被设为 pass_rate 并作为主奖励；format 是独立日志，用于观察模型是否输出了代码块。
6. 为什么一个带 timeout 的 subprocess 仍不是安全沙箱？
它仍可能访问父用户可见的文件、网络、凭据和其他资源。timeout 只限制运行时间；安全执行还需要最小权限 container/VM、凭据清理、网络和文件挂载限制。
7. 从代码测试迁移到下一章的浏览器研究 Agent，最先失去的是什么？
“正确性等于测试断言”的清晰接口。搜索与引用任务还要定义证据是否相关、覆盖是否充分、引用是否真的支持结论，因此 verifier 必须处理证据而不只是程序输出。
