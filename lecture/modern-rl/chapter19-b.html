04同步与异步：把“互相等”改成“边生产边消费”

同步与异步不是“保守算法”和“激进算法”的别名，而是各阶段在时间上是否必须对齐。它们首先改变设备等待方式，其次才改变数据新鲜度。

SYNCHRONOUS · 同步

这一批全部生成完，再训练

生成 b0训练 b0生成 b1训练 b1

流程直观，策略版本边界清楚；但生成时训练端等待，更新时生成端等待，还必须等 batch 中最慢的 completion。

ASYNCHRONOUS · 异步

两组设备用 buffer 解耦

Rollout
生成 b0生成 b1生成 b2
Training
训练 b0训练 b1训练 b2

完成的轨迹立即进队列，learner 凑够 batch 就更新；两端重叠减少空闲，但训练时拿到的轨迹可能来自旧版本策略。

横轴是真实时间。同步时间线中生成与训练互不重叠；异步时间线里两条 lane 同时推进。收益来自重叠，不是一次 forward 或 backward 自己变快。

还有一种 colocated execution（共置执行）：同一组 GPU 在 rollout 格式与 training 格式之间轮换。它节省设备，但生成和训练仍不能真正重叠，还会增加模型分片格式切换。于是三种方式可以按问题选择：

方式设备安排主要收益新代价
同步同组 GPU 串行简单、数据较新、易复现双方互等，长尾拖整批
共置同组 GPU 轮换角色预算少时复用显存格式转换；仍无执行重叠
分离异步rollout 与 training 独立重叠执行，提高稳态吞吐队列、权重同步、样本陈旧

权重同步不是“保存一下模型”

训练进程产生新参数后，生成端必须接收它们。这个过程叫 weight synchronization（weight sync，权重同步）：把 learner 的某一版本 Actor 参数传播给 inference worker。传全量参数、只传 Low-Rank Adaptation（LoRA，低秩适配）产生的小型 adapter、通过 GPU 高速互联直传或写 checkpoint 再加载，花费可能相差几个数量级。

更棘手的是边界：一条长回答生成到一半时新权重到了，系统可以等当前请求完成、直接中断、在 token 间切换，或等整批结束。越强调吞吐，版本边界越难解释；越强调样本来自单一明确策略，等待越多。因此同步策略必须和轨迹元数据一起设计，不能只测传输带宽。

05异步没有消灭代价，只把等待换成策略陈旧代价

队列让训练端不再等最慢任务，却让“生成这条数据的策略”和“消费这条数据的策略”发生时间差。这个差必须先能度量，才谈得上容忍或修正。

policy staleness（策略陈旧度）指一条轨迹进入更新时，其生成策略落后于当前 learner 策略的程度。最简单的工程量是版本差：

$$\Delta v=v_{\mathrm{train}}-v_{\mathrm{gen}}$$

$v_{\mathrm{gen}}$ 是 rollout 元数据中的生成版本，$v_{\mathrm{train}}$ 是消费它时的当前版本。$\Delta v=0$ 表示版本一致；$\Delta v=3$ 表示 learner 已经更新了三次。版本差容易记录，却不直接等于行为差异：三次很小的更新可能比一次异常大更新更接近原策略。

因此还要比较一个实际动作在新旧策略下的概率。设轨迹由行为版本 $\pi_{\theta_{\mathrm{gen}}}$ 生成，训练时当前策略为 $\pi_\theta$，对应 token/action 的概率比为：

$$\rho_t^{\mathrm{stale}}= \frac{\pi_\theta(a_t\mid s_t)} {\pi_{\theta_{\mathrm{gen}}}(a_t\mid s_t)}$$

若旧策略与当前策略都给这个 token 概率 $0.20$，则 $\rho=1$；若旧策略给 $0.20$、当前只给 $0.10$，则 $\rho=0.5$。这说明当前模型已经不太会产生这一步，直接把旧轨迹当成当前策略样本会引入偏差。

别和 reference policy 混淆：这里的 $\pi_{\theta_{\mathrm{gen}}}$ 是“实际生成这条轨迹的旧 Actor 版本”；对齐训练里的 reference policy 是长期冻结、用于 KL 参照的模型。一个用于追踪数据来源，一个用于约束策略偏移，二者不是同一角色。

$\Delta v=0$，也不自动保证两端概率相同

即使 rollout 与 training 标注为同一权重版本，推理引擎和训练引擎仍可能因精度、算子实现或 Mixture of Experts（MoE，混合专家）的专家路由差异算出不同 log-probability。这叫training–inference mismatch（训推不一致）。例如生成端记录 $\log\pi_{\mathrm{gen}}=-1.61$，训练端重算为 $\log\pi_{\mathrm{train}}=-1.80$，则

$$\rho=\exp(-1.80-(-1.61))=\exp(-0.19)\approx0.83.$$

时间上没有落后，概率比却已偏离 1。因此版本检查负责发现“用了旧权重”，两端 logprob 对齐测试负责发现“同权重算出了不同概率”；PPO clipping 约束策略更新幅度，不能自动修复生成端已经记录错位的行为概率。

生产系统通常组合三道边界：

  1. 浅 buffer：先限制队列最多容纳几批，让经验不会无限排队。
  2. 版本过滤：保存 policy_version，超过最大 $\Delta v$ 就丢弃或重采。
  3. 截断修正：在算法允许时按新旧策略概率比调整权重，并限制极端比率，避免少数 token 产生爆炸更新。

它们分别在系统、数据和统计层控制风险。异步不是“允许任意 off-policy 数据”，而是在吞吐与新鲜度之间写下一个可监控、可拒绝的契约。

Insight 03

buffer depth 既是性能旋钮，也是统计旋钮

深队列能吸收短时抖动，让 learner 不断粮；同一个深度也延长了数据从生成到消费的时间，使行为策略与当前策略分离。

提高异步度时，吞吐曲线必须与版本差、概率比和丢弃率一起报告。否则“更快”可能只是更快地消费旧策略数据。

06实验：加速一个环节，瓶颈会不会真的移动？

固定每批 512 条 completion、每条平均 2048 个 response token。调节两端吞吐、奖励耗时、同步等待与队列深度，观察端到端节奏和策略陈旧怎样同时变化。

Question
训练吞吐翻倍，是否一定能把整条 RL 流水线提速一倍？异步重叠又会付出多少策略陈旧代价？
Prediction
默认配置中 rollout 最慢；只加速 training 几乎不改变异步批次间隔。提高 rollout 吞吐会移动瓶颈；加深 buffer 不提高瓶颈速率，却增大版本差。

先比较三条 stage bar，再读结果：最长 bar 决定异步稳态间隔。把 training 调快而最长 bar 不变，就是“优化了非瓶颈”；把 queue 调深而三条 bar 不变，却让 $\Delta v$ 上升，就是吞吐与新鲜度的分离。

实验里的陈旧度使用一个刻意保守的课堂近似：

$$\Delta v_{\mathrm{approx}}=q+\left\lceil\frac{T_w}{T_t}\right\rceil$$

它把队列前方已有的 $q$ 个 batch，与权重同步期间 learner 可能前进的版本数相加。真实系统是否能在同步时继续更新、一次 batch 更新几次、何时切换权重都由实现决定，所以线上必须记录真实 v_train - v_gen，不能用近似替代日志。

容易想错

“异步速度上界是所有阶段吞吐之和。” 不对。不同阶段处理的是同一批数据的不同工序，不能把 token/s 相加。流水线每隔多久能产出一批，仍受最慢 stage 的服务时间限制。

07GPU utilization 是症状，不是终极目标

“GPU 99%”可能表示真正做了有用矩阵乘，也可能表示 kernel 很忙却没有产生可用于学习的新鲜轨迹。先把几个常见比例放回因果链。

最直观的 GPU utilization（GPU 利用率）是采样窗口内设备有 kernel 执行的时间比例。课堂里用 active share 近似：

$$U_i=\frac{T_{i,\mathrm{busy}}}{T_{\mathrm{window}}}$$

若异步批次间隔为 46.7 秒、training 只忙 13.1 秒，那么训练端 active share 约为 $28.1\%$。它没有说明 backward kernel 慢，而是说明 learner 大部分窗口里在等 rollout。此时继续优化训练 kernel，反而会让它更早做完、等待更久。

Model FLOPs Utilization（MFU，模型浮点运算利用率）进一步比较实际模型 FLOPs 与硬件峰值 FLOPs：

$$\mathrm{MFU}=\frac{\text{实际模型 FLOPs}}{\text{峰值 FLOPs}\times\text{墙钟时间}}$$

MFU 低可能来自通信、padding、数据加载、同步或负载不均；MFU 高也只说明计算单元忙，不证明 reward 正确、样本新鲜或验证集变好。要把指标分成三层读：

层先看什么它能回答它不能证明
学习结果独立评测、成功率、回归集模型是否真的变好系统为何慢
数据与策略reward、KL、entropy、$\Delta v$、丢弃率学习信号是否健康、新鲜哪张卡在等待
系统效率stage time、tokens/s、queue depth、GPU/MFU时间花在哪里高 reward 是否代表真能力
Insight 04

高利用率是约束下的手段，端到端有效学习才是目标

把低利用率归因到具体等待以后，才知道该加 rollout GPU、缩短 verifier、平衡序列长度，还是优化通信。单独追求“卡更忙”甚至可能生成更多过期或无学习信号的数据。

最终应优化“单位墙钟时间带来的独立评测增益”，吞吐、MFU 和 GPU utilization 只是解释这个目标的中间指标。
