Chapter 19 · Industrial-scale LLM reinforcement learning

算法进入大规模集群后，真正瓶颈在哪里？

上一章已经能用过程奖励与搜索比较多条推理路径。可是一旦每道题要采样多条长回答，真正拖慢训练的往往不再是 PPO 或 GRPO 的那一行损失，而是谁生产轨迹、谁消费 token、谁在等新权重。本章把“算法”放进一条会排队、会空转、会过期的真实流水线。

本章核心问题：怎样从每段耗时、生产/消费速率和策略版本差，定位大模型 RL 的系统瓶颈？提高吞吐时，怎样避免把新鲜的 on-policy 数据换成大量陈旧经验？

01搜索出了更好的路径，为什么训练机仍可能大半时间在等？

Chapter 18 解决的是“多条候选路径里怎样选”；本章先问一个更朴素的问题：这些候选路径来得够不够快，而且到训练时还新不新鲜？

取一个小而真实的训练轮次：64 道题，每道题生成 8 条回答，一共 512 条 rollout。假设生成用 45 秒，验证器打分用 4 秒，参数更新用 12 秒。若全部串行，一轮至少需要：

$$T_{\mathrm{step}}=T_{\mathrm{rollout}}+T_{\mathrm{reward}}+T_{\mathrm{train}}+T_{\mathrm{sync}}$$

即使暂时忽略权重同步，前三项也已经是 $45+4+12=61$ 秒。若把反向传播加速一倍，训练只需 6 秒，总时间却只从 61 秒降到 55 秒，提速约 $1.11\times$。原因不是训练优化做错了，而是 45 秒的生成阶段仍在原地。

Rollout45 s生成 512 条回答
Reward4 s验证与打分
Training12 s反向 + 更新

真正要观察的是耗时占比而不是哪段代码最“高级”：生成占 73.8%，因此只优化训练 kernel 不会显著改变端到端 step time。

这就是工业 RL 与普通监督学习的第一处分叉：监督学习从固定数据集读取样本；RL 的训练样本由当前策略在线生产。参数一变，下一批回答、奖励分布和 token 长度也会跟着变。系统不仅要算梯度，还要不断完成：

任务 / prompt
→
生成 rollout
→
验证与奖励
→
训练更新
→
同步新权重

顺着实线看样本流，最后再沿“同步新权重”回到生成端。任何一段变慢都会让相邻设备排队或断粮；这条闭环才是本章的分析对象。

容易想错

“多买 GPU 就会线性加速。” 只有新 GPU 被放到当前瓶颈上，并且没有制造更重的通信、同步或长尾等待时，端到端吞吐才会接近线性提高。把卡加到非瓶颈阶段，通常只是让更多设备更快做完、然后一起等待。

Insight 01

工业规模首先改变的是执行图，不是目标函数

PPO 仍用 Critic/GAE 与 clipped objective，GRPO 仍用组内相对信号；放大以后新增的是独立进程、队列、权重版本与失败恢复。

先把一轮训练画成时间线，再决定优化算法、kernel 还是系统。否则很容易把非瓶颈加速得漂亮，却没有缩短一次有效更新所需的墙钟时间。

02先拆出三类 worker：生产样本、消费样本、给策略行动

worker 不是某一种框架专有名词，而是一个长期运行、反复承担同类职责的进程。先按职责拆开，框架名才不会遮住数据究竟怎样流动。

PRODUCER

Rollout worker（轨迹生成进程）

读取 prompt，用某一版本的策略生成 completion；记录 token、mask、采样参数、旧 log-probability 和策略版本，再把轨迹交给奖励端。

CONSUMER

Training worker（训练进程）

从 buffer 取出已评分的 batch，计算 PPO/GRPO 所需统计量、反向传播并更新参数；它消费的是 token batch，不直接面对用户。

ACTION SERVICE

Inference worker（推理进程）

执行模型前向并逐 token 采样。它可以被 rollout worker 调用；规模扩大后常由专用生成引擎承担，以管理 key–value cache（KV cache，键值缓存）、连续批处理和长尾请求。键值缓存复用此前 token 的注意力中间量，避免每生成一个新 token 都重算整个前缀。

真正要分清的是职责而非进程名：rollout 负责组织“要生成哪些训练样本”，inference 负责高吞吐执行模型前向，training 负责把已评分样本变成参数更新；小实验里三者可以挤在一个 Python 进程中。

为什么把 rollout 与 inference 分开说？因为它们处在不同抽象层。rollout worker 知道“每道题采样 8 条”“何时算一条轨迹结束”“使用哪个 policy version”；inference worker 更关心 prefill、逐 token decode、KV cache 与 batch 调度。前者定义训练样本，后者高效执行生成。两者可以一一对应，也可以许多 rollout 任务共享一组 inference engine。

PPO 与 GRPO 在这里发生了什么变化？

本章不重新推导算法，只回顾它们占用了哪些系统角色。PPO 通常还要运行 Critic，并计算 reference log-probability、奖励、优势与策略更新；GRPO 省掉 Critic，用同一 prompt 下多条回答的相对奖励构造学习信号。二者都没有省掉最昂贵的共同环节：先由当前策略生成大量 token，再把新权重送回生成端。

03统一单位以后，瓶颈才可以被计算

“rollout 很慢”“训练很快”不是诊断。先把工作量、速率与时间写成同一套量纲，才知道哪个反事实真能缩短一轮。

假设一批有 $P$ 个 prompt，每个 prompt 采样 $G$ 条 completion，平均每条生成 $L$ 个 response token，则生成工作量近似为：

$$N_{\mathrm{tok}}=P\times G\times L$$

若 rollout 端的生成吞吐为 $v_r$ token/s，训练端消费吞吐为 $v_t$ token/s，两段的理想时间分别是：

$$T_r=\frac{N_{\mathrm{tok}}}{v_r},\qquad T_t=\frac{N_{\mathrm{tok}}}{v_t}$$

这里刻意使用相同的 response token 工作量做课堂近似，方便比较速率；真实训练还会计算 prompt token、reference forward、多个 epoch、padding 与通信，所以必须从 profiler 读取每段实测时间，而不是把这个估算当成账单。

串行时看“总和”，流水线稳态看“最大值”

同步执行时，各阶段不能重叠，一批的时间近似相加。把 rollout 与权重同步看成生产端阶段、训练与奖励各看成一段，异步流水线填满后的理想批次间隔近似由最慢一段决定：

$$ T_{\mathrm{sync}}=T_r+T_{\mathrm{reward}}+T_t+T_w, \qquad T_{\mathrm{pipe}}\approx\max(T_r+T_w,\;T_{\mathrm{reward}},\;T_t) $$

$T_w$ 是生成端停下来接收新权重的时间。第一式回答“一批从头到尾多久”；第二式回答“流水线填满后，平均隔多久交付一批”。后者只是理想上界：队列抖动、长尾 completion、跨机通信和显存抢占都会让真实间隔更长。

如果把批次统一为“已评分 rollout batch”，生产率为 $\lambda_r$ batch/s，训练消费率为 $\mu_t$ batch/s，队列深度 $q$ 的变化可以写成最小守恒关系：

$$\frac{dq}{dt}=\lambda_r-\mu_t$$
  • $\lambda_r<\mu_t$：训练端会断粮，training GPU 等样本。
  • $\lambda_r>\mu_t$：buffer 会不断变深，暂时不丢吞吐，却让样本越来越旧。
  • $\lambda_r\approx\mu_t$：长期稳态才可能既不饿死 learner，也不无限积压。
Insight 02

系统吞吐由瓶颈速率守恒，不由最快设备决定

生产者比消费者慢，learner 无数据可学；生产者比消费者快，队列积压并让策略数据逐渐陈旧。只有两端速率接近，额外算力才真正转化为新鲜样本吞吐。

监控时同时画 rollout 产出率、training 消费率和 buffer depth。只看某一组 GPU 的 tokens/s，会漏掉数据是在断流还是在过期。
